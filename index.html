AI Engine Guide

Important system rules, security behaviour and tips.

One Key = One Device (Multi-login Prevention)
  • The first device that successfully unlocks a key permanently binds it.
  • Any other device trying the same key is blocked with “This key is already used on another device”.
  • Works for both normal DGXEN- keys and Master Keys.
  • Same device can log in again without increasing usage count.
App Version Code — when it is read

Source: native Auth.getAppVersionCode() → PackageManager real installed versionCode (not spoofable from JS).

  • Every app open — reportAppVersionCode() saves to Firebase knownDevices; killswitch watcher starts.
  • Realtime — settings/appUpdate listener; admin Force Update / Killswitch changes apply live.
  • Before unlock — after key OK, shouldBlockUnlockForForceUpdate(); stale + Force Update = unlock blocked.
  • After key success — reportAppVersionCode(uid) updates device/user version again.

Short: not only on key insert — open + live + unlock, all three.

Admin Login Secret (Code Entry)
  • On the Admin Access screen, the code field is hidden by default.
  • Secret: press and hold the FINGERPRINT button for 10 seconds — the admin code entry will appear.
  • A short tap on FINGERPRINT still runs normal fingerprint unlock.
  • Prefer fingerprint when enrolled. Code is fallback (hold FINGERPRINT 10s).
Share/User Logs & Key Banning
  • Every key generation is logged automatically (generator name + key), not just sharing/re-use.
  • When a second device tries a bound key, a separate share/re-use log is created too.
  • Sharing logs show: Generator Name → sended key to → Receiver (or unknown user).
  • Fast Generation flag: if a device sets its name and generates its key within 1 minute of each other, that entry gets a red "⚠ FAST GEN <1m" badge, a red outline, and shows in the critical banner at the top of this section — this is informational, meant to surface likely automated/scripted registrations, and does not block anything by itself.
  • Use BAN KEY to blacklist that key. It appears in Banned Normal Keys.
  • Click KEY BANNED again to unban the key.
  • Banned keys show “Banned: …” on the login screen (not a device ban).
Master Keys Behaviour
  • First device binds the master key and increments usage once.
  • Same device can reuse the master key without extra count.
  • Deleting a master key in admin also wipes its usage and device tracking.
Active Users vs Registered Users
  • Active Users = currently have a live (non-expired) key. Live countdown is shown on the right.
  • Registered Users = all non-banned devices that ever registered.
  • Click any name / ID / key to copy it instantly.
Tips & Best Practices
  • Always hard-refresh (Ctrl+Shift+R) after updating login or admin files.
  • Use the top Refresh button or enable Auto Sync for live data.
  • If a legitimate user changes phone, use System Reset → Unbind Device.
  • Clear old Share Logs with the CLEAR ALL LOGS button when needed.
  • Key device track auto-cleanup: when a user generates a new key on the same account, the old key's device-track entry is deleted automatically so Firebase does not fill with expired keys.
  • Global Kill (System Reset tab): turns on a network-wide critical shutdown — all online apps show “Critical shutdown” and close in 10s. Needs double confirm + fingerprint.
  • Master keys should be kept private — they still follow the one-device rule.
Cloud Storage Download Limit (B2)
  • Backblaze B2's free tier includes 1024MB (1GB) of download bandwidth per day across the whole bucket.
  • Once that daily quota is used up, further file downloads are temporarily blocked — uploads and other admin functions are unaffected.
  • The block is not permanent: it resets automatically the next day (B2's UTC billing day rollover), no action needed.
  • If downloads suddenly fail for everyone at once, this daily cap is the most likely cause — check again after the reset before assuming it's a bug.
Anti-Bypass & Access Control
  • Core Pipeline Interception: fragile UI-level blocking (overlays/dialogs) has been replaced with direct code-level execution gates inside MainActivity.smali.
  • Method Gatekeeping: a strict state check (Auth.unlocked) is injected at the exact entry points of critical execution methods (checkOverlay and checkVpn).
  • Macro & Automation Defeat: neutralizes high-speed macro tools (like MacroDroid) and UI race conditions — even if an automated trigger simulates a button tap instantly on screen wake, execution is hard-stopped (return-void) at the code level unless the static authentication flag evaluates to true.
  • Reliability: guarantees zero-bypass functionality without causing UI rendering delays, black screens, or activity verification crashes.
  • Background session lock: if the admin panel sits in the background (tab switched away / app minimized) for 10+ minutes, it's automatically signed back out to the login gate on return, requiring a relogin. Time spent actively in the foreground is never counted, no matter how long — this only ever triggers from background time.
